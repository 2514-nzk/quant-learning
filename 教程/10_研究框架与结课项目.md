# 第 15 章｜研究记录与可复现项目

你已经会：整条研究流程和运行脚本。这一章只问：一个月后，还能找到那次数据、设置和输出吗？

一个月后，你打开电脑，想向小林解释第一笔盈利。屏幕上只剩一张写着“4%”的截图。

你已经知道至少四种第一期期末金额：8,320.00、8,200.00、8,303.38、8,191.61 元。截图里是哪一种？C 买到了吗？费用付过几次？

先猜：只看那张截图，能判断吗？

<details>
<summary>展开核对</summary>

不能。4% 是理想未扣费收益；C 是否买到、费用扣了几次，决定了期末是 8,320 还是 8,191.61。记录的意义，就是让这些问题有答案。

</details>


**研究记录其实像做菜写菜谱。** 今天放了多少盐、用了什么食材、烤了几分钟，如果不记，下个月即使做出了同样的味道，也不知道为什么，更难排查失败的原因。


## 1. 数据、代码与输出归档

这次你没有从装一个复杂框架开始，只收起真正用过的材料：

```text
data/story/rounds.csv           固定的每期输入与答案
data/story/price_history.csv    第一期的过去价格指数
examples/story_research.py      同一套演算与模型比较
outputs/story/report.json       自己这一遍的实际输出
```

先分清它们各自是什么：前两个是输入，脚本是计算过程，报告是这一次的输出。仓库里的 `data/story/model_results.json` 是编书时的参考运行；自己的报告另存，别把两者混成同一份证据。

你可以先用同样的命令重做：

```powershell
python examples/story_research.py --models --output outputs/story/report.json
```


### 只有一张“赚了 320 元”的截图，会漏掉什么？

你把这次实验想成一份菜谱，至少得写出：

| 菜谱里要写 | 对应研究中要保存 |
|---|---|
| 用了哪些食材 | 用的是哪份数据、哪几个历史版本 |
| 放了多少调料 | 用了哪些因子、参数、费率 |
| 具体步骤 | 哪天选股、哪天买卖、怎么处理买不到 |
| 最后成品 | 逐期收益、现金、持仓与模型报告 |

第一次理想全成交、不扣费，期末 **8,320 元**；如果 C 买不到且双边扣费，约 **8,191.61 元**。同一组信号，仅仅成交与成本设定不同，结果就不同。

<details>
<summary>检查题：两个人的回测都写“收益 4%”，能说结果完全可复现吗？</summary>

不能。要核对两人是否用了同一份输入、同一交易时点、同一成交假设和同一费用。只有终点数字相同，并不足以证明过程相同。

</details>


## 2. 文件指纹、环境与配置

小林说自己没改代码，你也觉得数据一样。你们先查报告里的输入与脚本指纹，以及 Python、NumPy、pandas、scikit-learn、LightGBM 版本。

**指纹**是由文件内容计算的一串识别值。它帮助确认“是不是同一份”，不会证明内容本身正确。本脚本统一文本换行后计算，避免 Windows 与 Linux 仅因换行不同而产生差别。

再查记录的特征列、训练/验证/测试期数、随机种子、候选设置、选中的参数和每侧费率。只有比较对象相同，两次结果的差异才有清楚的起点。

## 3. 实现范围与工程边界

这份报告确实保存了实际模型输出，也能重放 R01 的现金与双边费用。

但第 9 章的延迟卖出只做了时间冲突设计题；整手、最低佣金、税费历史、公司行为、部分成交和逐日订单账本没有在故事脚本里实现。

你给报告加了“已计算”和“尚未实现”的区别：

| 已计算 | 尚未实现 |
|---|---|
| R01 的买入、未成交现金与双边费用 | 整手、最低佣金、真实税费历史 |
| 四期收益、基准与 RankIC | 公司行为、部分成交 |
| 模型训练、验证与测试 | 逐日订单账本、延迟退出 |
| 输入与脚本指纹、环境记录 | 真实市场快照接入 |

读者这样才能知道哪一页可以拿输出复核，哪一页仍是在设计下一步工程。

原有 `src.run_demo` 使用较大合成日频面板与七个量价/规模特征；真实快照入口和月度三因子项目也各有范围。它们在[工程实现参考](参考_组合与项目实现.md)中查阅，不拿它们的净值替换本故事的成绩单。

## 4. 实验版本与失败记录

你在笔记里保留：M0 的四期结果、三列平均的探索、候选森林三档深度、LightGBM 三档树数，以及测试中复杂模型没有胜出的那张表。

当你想到新方案时，先记录“这次相对哪版改了什么，为什么值得改，准备到哪里评价”。一个版本一个输出位置，不用最后最好的截图覆盖全部尝试。

这时[实验日志](../templates/experiment_log.csv)和[研究问题表](../templates/research_question.md)才有了用处。它们承接实际过程，不要求刚起步就先填一堆空白表格。

## 5. 研究报告与证据追溯

试着只用四段话讲这次研究：

1. 想检查什么，统一规格是什么；
2. 用了哪些数据，时间边界在哪里；
3. 关键对照是什么，哪些结果不利；
4. 目前支持到哪里，哪些事情仍没实现。

遇到一个数字，小林应该能顺着文件找到它的输入、计算和设置。能做到这里，再回到第一页，你会用和刚开始不同的眼光看待那 320 元。


## 选读｜进阶训练：一份真正可被另一个人重做的实验包

**入门关**：保留输入文件、代码、运行命令和输出路径，不要只保留最好看的图。

**进阶关**：为每次实验输出一份清单，最少包括：

~~~text
run_id / run_time
research_question / frozen_protocol_version
data_snapshot / data_hash / historical_universe
feature_set / label_definition / point_in_time_cutoff
train_valid_test_windows / purge_policy
candidate_parameters / selection_rule / chosen_model
cost_model / executable_assumptions
software_versions / random_seed / outputs / failures
~~~

文件指纹能帮助核对“是不是同一文件”，但不能保证原数据真实、时点正确。环境版本、浮点运算和随机数差异也会影响部分模型输出。

**研究关**：请另一人或另一台环境从干净目录按清单重跑。只要需要向作者追问“这个输入从哪来”“当时可用时间是什么”“这一版是否试过测试集”，报告就还有无法独立复现的缺口。

把负结果同样归档。每种改动都有一个可追溯的版本，不要只更新 README 中最好的数字，旧配置和旧输出却被覆盖。

**本章交付**：从原始输入到结论的完整目录、运行命令和一次他人复核记录。
